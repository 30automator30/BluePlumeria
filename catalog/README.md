# Catalog pipeline

The storefront (`docs/shop.html`) is static — Snipcart charges the price baked
into that HTML and validates it by crawling the page **without running
JavaScript**. So every price must physically be in the static file. This
pipeline keeps that true while letting the owner manage the catalog from the
admin.

## Source of truth: Supabase

The owner adds pieces, uploads photos, sets prices, and orders the catalog in the
Owner Dashboard (`docs/admin.html`). **Supabase is the full source of truth.**
`catalog/products.json` is a **generated snapshot** — do not hand-edit it.

| Data | Where it's edited |
|------|-------------------|
| price, availability, name, label, collection, tier, **photos, order, which pieces exist** | Owner Dashboard → Supabase |
| the storefront HTML / DB seed | generated by the scripts below |

Photos live in the public Supabase Storage bucket `product-images` (owner-only
write). The storefront and Snipcart load them by public URL.

## How an admin edit reaches the live store

```
Owner edits/adds in the admin  ─▶  Supabase (products table + Storage)
                                        │
        GitHub Action "Publish store"   │ (every ~10 min, or "Run workflow" now)
                                        ▼
  sync-from-supabase.py  ─▶  regenerate products.json from the DB
                             (published + complete pieces, ordered by position)
  gen-shop.py            ─▶  regenerate the cards in docs/shop.html
  gen-seed.py            ─▶  regenerate supabase/seed_products.sql (bootstrap only)
                                        │
                          commit (only if changed) ─▶ GitHub Pages redeploys
```

**Draft → Publish:** a new piece is a draft until it has a photo + a price and
the owner clicks Publish. Only published + complete pieces are rendered.

**Floor guard:** `sync-from-supabase.py` refuses to write (fails the CI run) if
the published catalog would drop to zero or shrink drastically — so a bad query
or an accidental mass-unpublish can't silently wipe the store. Override for an
intentional bulk removal with `ALLOW_CATALOG_SHRINK=1`.

## Scripts

- `sync-from-supabase.py` — regenerate `products.json` from Supabase (public read
  key; no secret). Full-generate with the floor guard.
- `gen-shop.py` — regenerate the product cards in `docs/shop.html`.
- `gen-seed.py` — regenerate `supabase/seed_products.sql` (bootstrap/DR snapshot;
  `ON CONFLICT DO NOTHING`, never overwrites live data).
- `_backfill_shape.py` — one-time helper that migrated the old path-string image
  model to `[{url,alt}]` + `aiNote`/`position`/`published` (kept as a record).
- `extract-from-shop.py` — the original one-time bootstrap (kept for reference).

## Data model (per product)

`sku, name, price, collection, tier, label, maxQuantity, itemUrl, cartImage,
images:[{url,alt}], available, aiNote, position, published`

- `collection` ∈ sea-shore | stone-earth | pearl-crystal | hand-woven (DB CHECK).
- `tier` ∈ signature | everyday (DB CHECK). `everyday` renders as a single-photo
  card under its own banner.
- `aiNote` shows the "shown on an AI model" caption + lazy-loads (legacy AI-model
  shots). New pieces default `aiNote = false`.
- `position` orders pieces **within** their collection group (the storefront
  regroups by tier→collection). Reorder arrows in the admin swap positions.

## Migrations (apply in order in the Supabase SQL editor)

1. `20260819120000_catalog_admin_fields.sql` — position/published/ai_note,
   taxonomy CHECKs, published-only public read, `swap_positions` RPC, auto-position trigger.
2. `20260819120001_backfill_catalog_data.sql` — put the existing pieces in the new shape.
3. `20260819120002_product_images_storage.sql` — the `product-images` bucket + owner-write RLS.

## Notes

- Generated files are pinned to LF (`.gitattributes`) so local (Windows) and CI
  (Linux) output is byte-identical — no line-ending churn commits.
- GitHub disables scheduled workflows after 60 days of repo inactivity; re-enable
  "Publish store" in the Actions tab if the shop goes quiet that long (the manual
  "Run workflow" button always works).
